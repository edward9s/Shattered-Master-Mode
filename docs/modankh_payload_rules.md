# ModAnkh Injectable Payload Rules

[正體中文版](modankh_payload_rules.zh-TW.md)

## Purpose

ModAnkh and its debug/storage support code are not ordinary application code. They must work in two environments:

1. as part of Shattered Master Mode itself; and
2. after being extracted from a compiled SMM donor APK/JAR and injected into another SPD-derived build.

A change may compile and run correctly inside SMM while still breaking binary injection. Treat every class that can enter the injectable payload as a small compatibility library with stricter rules than normal game code.

The current implementations in `scripts/inject_apk.py` and `scripts/inject_jar.py` are the source of truth for the exact payload boundary and compatibility checks.

## 1. Payload boundary

Keep the injectable surface narrow and deliberate.

Important payload families currently include:

- `com.spd.mod.items.ModAnkh`
- `com.spd.mod.items.ModAnkhStore` and its `$*` classes
- `com.spd.mod.mechanics.ModDebug` and its `$*` classes
- explicitly supported helpers such as `ModValueSearch` and `ModSaveTransfer`
- `com.spd.mod.mechanics.ModAssassinBuff` plus its required `ModAssassin` / `ModFlash` class families, for Debug Console `affect` support

Do not assume that every donor class reachable from these classes is safe to copy into a target build.

The APK and JAR injectors also detect the target SPD-family package root from the `Dungeon` / `Hero` / `HeroClass` / `Item` / `Level` / `GameScene` class structure. If a fork has renamed the upstream package (for example Rat King Adventure), donor references and reflection strings are rebased to that target root before compatibility validation. `com.spd.mod.*` payload names themselves are never renamed.

### Rules

- Prefer self-contained helpers under an existing payload family.
- If a helper must be added, make its inclusion explicit and verify both APK and JAR injectors.
- Never make payload code depend on unrelated donor-only application classes.
- Never rely on an obfuscated donor class name being meaningful in the target.
- Do not broaden the payload merely to silence a compatibility error.

## 2. R8 / desugaring safety

Binary donors are sensitive to the shape of optimized bytecode. R8/D8 may rename, merge, outline, or share compiler-generated helpers across otherwise unrelated application code. If the injector follows one of those donor-only dependencies blindly, unrelated donor code can enter the payload and later fail target compatibility validation.

A typical symptom is a chain of relocated classes named like `ModDebug$Donor_*` that unexpectedly reference unrelated LibGDX members or other donor-specific APIs.

### Important lesson from the fuzzy-console incident

The introduction of broader fuzzy identifier support changed the generated bytecode enough to expose this problem, but the fuzzy feature itself was not proven to be the root cause.

In particular, an earlier working version of `ModDebug$Console` already used constructs such as `removeIf` with lambdas and still injected successfully. Therefore:

- do not conclude that a lambda, method reference, or Java 8 collection method is automatically the cause merely because a later build fails;
- treat those constructs as risk indicators only;
- first compare the complete donor build pipeline and R8 rules between the last working build and the failing build.

### Prefer predictable payload code

When there is no strong reason to use a more indirect construct, prefer code whose compiled dependency graph is obvious:

- ordinary loops
- explicit `get` / `put` / `containsKey`
- ordinary helper methods
- anonymous inner classes when a callback/comparator is necessary

This is a robustness preference, not a claim that Java 8 features are inherently incompatible.

## 3. Donor build parity is mandatory

A donor APK is only valid if it was built with the same payload-preservation rules expected by the injector.

The Android build path must apply `patch_android.patch_proguard()` before the release build. That patch adds the `-keep` rules required to keep the ModAnkh/ModDebug payload stable under R8.

### Proven failure

The local `scripts/build.py` path previously called:

- `patch_gradle()`
- `patch_play_games_version()`
- `patch_manifest()`

but accidentally omitted `patch_proguard()`.

The CI path executed `scripts/patch_android.py`, which *did* apply `patch_proguard()`. This meant local and CI donor builds were not actually equivalent even though `build.py` claimed to follow the workflow.

Before the fuzzy expansion, the local donor happened to remain injectable despite the missing keep rules. After the fuzzy implementation changed the code shape, R8 produced a different result and the injector began discovering `ModDebug$Donor_*` dependencies with unrelated LibGDX references. Adding the missing `patch_proguard()` call to the local build restored successful injection.

### Rule

Whenever a local build script claims parity with CI, verify the actual patch sequence rather than trusting the comment or intended design.

For Android donor builds, the effective pre-build sequence must include the payload ProGuard patch.

## 4. Target API compatibility

Do not assume that every SPD fork exposes exactly the same source API as the current SMM donor.

### Rules

- Treat target API differences as normal.
- Use direct calls only for APIs stable enough across supported targets.
- For known compatible API variations, adapt them deliberately in the injector.
- For optional or unstable APIs, prefer reflection/capability probing when practical.
- Keep reflection focused; do not create large compile-time dependency graphs unnecessarily.
- If compatibility validation reports a real missing executable reference, fix the payload or add a deliberate adapter. Do not weaken the validator just to make injection continue.

Example: `Item.setCurrent(Hero)` may be adapted to older `curUser` / `curItem` fields when the target exposes that older API.

## 5. Debug Console consistency

Debug Console behavior should not depend on how a command reaches the executor.

Keep these paths behaviorally consistent where applicable:

- direct interactive commands
- macros
- `@handle` result prefixes
- optional methods on `give`, `spawn`, and `affect`
- reflection-based `get` / `set`
- `use`

### Fuzzy identifier policy

Names users reasonably need to remember may use fuzzy resolution:

- class names
- field names
- method names
- `Class`-typed method arguments
- enum values used as named values

Matching order:

1. exact
2. unique prefix
3. unique substring
4. compact ordered subsequence
5. ambiguous best result: show `Similar:` suggestions and do not guess

Exact names always win. If an exact method name exists but its arguments are invalid, do not silently redirect to another fuzzy-matched method.

#### Ordered fuzzy matching

The fuzzy tier is deliberately stricter than a plain subsequence search:

- query letters must appear in the candidate in the same order;
- queries shorter than 3 characters do not use subsequence fuzzy matching;
- the total skipped characters inside the matched span must be at most `max(4, query length)`;
- the matched span must be no more than twice the query length;
- lower scores are better, with skipped-character gaps carrying the strongest penalty;
- earlier starts, CamelCase/word-boundary hits, and shorter candidates act as tie-breakers.

For operations that must choose one identifier (class, field, method, enum), only candidates tied for the best fuzzy score remain eligible. A unique best score may be auto-resolved; equal best scores remain ambiguous and produce `Similar:`. `inspect` may display multiple qualifying fuzzy matches, but they are ordered by match quality.

Examples that should remain useful include `goem` → `Golem`, `potheal` → `PotionOfHealing`, `ringenergy` → `RingOfEnergy`, and `atk` → `attack`. A query whose letters are scattered across a long unrelated identifier should be rejected by the gap/span limits.

#### Class-name search scope

Unqualified class queries fuzzy-match **only the simple class name**. Package names must not contribute letters to a fuzzy match.

A query is treated as qualified only when it explicitly contains `.` or `$`; only then may the full qualified/binary class name participate in fuzzy matching.

This prevents results such as `etchain` being suggested as `ScrollOfRecharging` merely because letters can be collected from `com.shatteredpixel...items.scrolls.ScrollOfRecharging`. For an ordinary `etchain` query, only `ScrollOfRecharging` itself is considered, so that candidate does not match.

The following remain exact by design:

- command verbs
- `@handle` names
- numbers, cells, quantities, durations
- ordinary string arguments

## 6. APK injector invariants

Unless a deliberate architecture change says otherwise:

- the target APK remains the base artifact
- target package identity remains unchanged
- original target DEX files remain byte-for-byte unchanged and are shifted behind the overlay DEX
- the overlay contains only the patched/injected payload
- target resources remain untouched except for deliberate manifest edits owned by the injector
- target API compatibility is validated before packaging
- unresolved/self-containment failures stop injection

Do not solve a payload problem by rebuilding or broadly mutating the target APK unless that becomes an explicit architectural decision.

## 7. JAR injector invariants

The desktop JAR injector follows the same isolation principle:

- target JAR remains the base
- only explicitly selected ModAnkh/debug payloads are copied
- `Dungeon.init()` is patched at the known anchor
- compatible API differences may be adapted deliberately
- unrelated target entries are preserved
- stale signature/index metadata may be removed when required by repackaging

Changes to payload structure must be checked against both injectors. APK success alone is not sufficient.

## 8. Validation requirements

Before considering a payload change complete:

1. Compile the changed Java sources.
2. Verify the donor build path applies the same payload-preservation patches as CI, especially `patch_proguard()` for Android release builds.
3. Inspect the resulting ProGuard rules when debugging R8-related failures; do not assume they were applied merely because the helper function exists in the repository.
4. Build a fresh SMM donor artifact. An old donor still contains old R8 output.
5. Run the applicable injector against at least one representative target.
6. Ensure no unexpected `ModDebug$Donor_*` or other relocated helpers appear.
7. If relocated helpers do appear, trace why they entered the dependency closure before changing the allowlist or validator.
8. Confirm compatibility validation passes without suppressing legitimate errors.
9. Exercise the affected runtime feature in the injected build when possible.

A source-only compile is necessary but not sufficient for binary-injection changes.

## 9. Failure diagnosis

Classify the failure before modifying code.

### `missing target method/field/type`

Determine whether the reference is:

- a legitimate target API difference that needs an adapter;
- an unstable API that should use reflection/probing; or
- an accidental donor dependency that should not be in the payload.

### Many unrelated LibGDX/API failures from `ModDebug$Donor_*`

Do **not** immediately blame the most recent source construct.

Check in this order:

1. Was the donor rebuilt from the current source?
2. Did the exact build path apply `patch_proguard()`?
3. Are the expected payload `-keep` rules present in the effective Android ProGuard configuration?
4. Did local and CI build paths diverge?
5. Only then inspect recent source changes for R8/desugar-sensitive constructs or new dependency edges.

The fuzzy-console incident demonstrated that a source change can merely expose a build-pipeline bug that already existed.

### `donor-only dependency ... is not present`

The payload references a class the donor-closure logic cannot safely carry. Remove the dependency, explicitly redesign the payload boundary, or make the dependency self-contained.

Do not disable self-containment checks as a shortcut.

## 10. Repository write rules

This repository has a strict public-attribution requirement:

> Any publicly visible attribution produced by repository changes must show only `edward9s`.

This applies to commit authors/committers and any public contributor/activity identity created by the workflow.

Therefore:

- do not create a branch unless the user explicitly requests one
- do not open a PR unless the user explicitly requests one
- do not create temporary/test refs, no-op commits, or throwaway workflow files
- do not use GitHub Actions/bots to commit or push
- do not use another account or GitHub App identity for repository writes
- do not add `Co-authored-by` metadata for another identity
- use only a write path whose resulting author and committer can be verified as `edward9s`

Force-push or history rewriting is allowed when needed. The hard rule is public identity and avoiding unnecessary public repository records.

## 11. Design principle

When choosing between a clever implementation and a slightly more explicit one, prefer the implementation whose compiled dependency graph and build requirements are easier to audit.

For ordinary SMM code, source-level correctness may be enough. For injectable ModAnkh payload code, the compiled APK/JAR dependency graph **and the donor build pipeline** are part of the compatibility contract.
